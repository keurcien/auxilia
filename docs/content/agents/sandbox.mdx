# Using the Sandbox

This page is the **agent-author's view** of the sandbox: how to give an agent code execution, what tools the LLM gains, and how the sandbox behaves across a conversation.

If your workspace has no sandbox yet, a workspace admin needs to add one under **Settings → Sandboxes** first — see **[Sandbox — Setup](/deploy/sandbox/setup)**. Agent authors only bind it.

## Give an agent code execution

1. Open the agent and click **Edit**
2. In the **Tools** section, click **Add tool**
3. Below the MCP servers, pick a **sandbox** and click **Add**
4. **Save changes**

An agent binds **one** sandbox. From the next message on, every run of the agent has a live sandbox: **auxilia** opens it before the model sees the conversation — there is nothing for the LLM to create or connect.

![Add tool dialog with a sandbox](https://pub-7a6e8912b3c448b8a8bfa47a0363f7bc.r2.dev/docs/agent-add-tool-dialog.png)

## What the agent gains

A sandboxed agent runs on deepagents' harness. On top of its MCP tools it gets:

| Tool | What it does |
| --- | --- |
| `execute(command, timeout=None)` | Run a shell command in the sandbox; returns stdout + stderr and the exit code. Commands are cut off at the sandbox's per-command **timeout** (default 30 minutes) with exit code `124`. |
| `ls(path)` | List a directory |
| `read_file(path, offset=0, limit=2000)` | Read a file with line numbers, paginated |
| `write_file(path, content)` | Create a file (fails if it exists — use `edit_file` to change one) |
| `edit_file(path, old_string, new_string, replace_all=false)` | Exact string replacement inside a file |
| `glob(pattern)` | Find files by pattern, e.g. `**/*.py` |
| `grep(pattern, path=".")` | Regex search over file contents |
| `write_todos` | Keep a plan for multi-step work (rendered in the chat) |
| `task` | Delegate a sub-task to a general-purpose helper that has the same tools and skills |

All file tools operate on the sandbox's filesystem, never on the **auxilia** host. The packages listed as **Default packages** on the sandbox are pip-installed when a sandbox is created, so the agent doesn't have to.

## One sandbox per thread

The thread remembers its sandbox. At the start of every run **auxilia**:

1. **Reconnects** the thread's sandbox if it still exists — files written in earlier turns are there, and on OpenSandbox the 30-minute lifetime is renewed; on Daytona a sandbox that auto-stopped while idle is started again
2. **Replaces** it with a fresh one if it is gone (expired, deleted, or lost with its host and no snapshot) — the model receives a host notice saying the earlier files are gone, so it recreates what it needs instead of assuming
3. **Creates** one on the first run of the thread

At the end of each turn the sandbox state is persisted where the provider supports it (Cloud Run sandboxes snapshot to GCS). A new thread always starts with a new sandbox.

## When the sandbox is unavailable

If the sandbox provider does not answer — wrong credentials, quota, outage — the agent is **not ready**: the chat replaces the composer with a notice, and a run launched over the API is refused with a `409 sandbox_unavailable`. The model never runs without the sandbox it was configured with, and never sees the outage. Fix the sandbox under **Settings → Sandboxes** and the agent recovers on its own.

## Skills and scripts

Skills with `scripts/` need a sandboxed agent: the run uploads every enabled skill to `/tmp/auxilia-skills/<skill-name>/` in the sandbox, and the system prompt lists the scripts by absolute path, so the agent reads the `SKILL.md` and runs the script in two tool calls. See [Skills](/agents/skills).

## Typical usage pattern

A data-analysis agent's turn looks like:

1. `write_file("/tmp/analysis.py", "...")`
2. `execute("python /tmp/analysis.py")`
3. `read_file("/tmp/result.json")`

Because the sandbox lives for the length of the thread, later turns can just `execute` or `read_file` without rebuilding state. The [tool call](/agents/tools#tool-calls-in-chat) for each step shows up in the chat's **Worked** timeline.

## MCP tools from sandbox code

An agent with both a sandbox and MCP tools can use either direct tool calls or
Python code. Tool permissions are identical: disabled tools are unavailable,
**Always allow** tools run immediately, and **Needs approval** tools wait for the
user's decision in chat. There is no additional connection setup for users.

```python
import auxilia_mcp as mcp

# Same exact tool names and schemas as direct calls.
print(mcp.tools())
result = mcp.call("your_server_your_tool", {"argument": "value"})
if result["is_error"]:
    raise RuntimeError(result["content"])
data = result["structured_content"]

# Save the result already fetched, without invoking the tool again.
import json
from pathlib import Path
Path("/tmp/result.json").write_text(json.dumps(result), encoding="utf-8")
```

`mcp.call_to_file(tool_name, arguments, path)` is an alternative that invokes the
tool once and saves its result. Use it instead of `call`, not to save a result
you have already fetched. Both methods enforce the configured result-size limit
(16 MB by default), regardless of the size threshold used for context offloading.

Results contain `content`, `structured_content` and `is_error`. The bridge writes
results directly to sandbox files; only metadata and paths go through Redis.
Code can transform those files and print a small summary. Direct calls continue
to work and are useful for individual actions and model-visible results.

If an MCP call requires OAuth interaction, chat displays **Connect** while the
script waits. After the existing OAuth callback successfully exchanges the code,
the bridge reconnects and retries only that authentication-blocked call. Approval
requests show the exact tool and arguments. These live requests are available in
the owning user's web chat, including after reloading it. A caller on another
surface can open that chat to answer them.

### Deployment

Set `SANDBOX_MCP_URL` to a backend URL reachable **from the sandbox**. It defaults
to `BACKEND_URL`; a development localhost URL will not work from a remote sandbox.
Permit outbound access to this host in your sandbox provider's network policy.
For Cloud Run, enable both the sandbox's egress setting and the gateway's
`ALLOW_EGRESS=true`. Use HTTPS outside local development.

The API accepts requests on any instance; the run worker services them using its
live MCP sessions. Redis coordinates requests and decisions, so sticky sessions
and a separate sidecar are unnecessary. Each sandbox-enabled agent receives a
random run-scoped capability with its own filtered toolset. Real MCP credentials
stay in the backend. Capabilities are revoked when the run ends; a short lease
expires them when the worker disappears. Shared parent/subagent sandbox processes
and files remain one trust boundary; separate agent capabilities do not isolate
mutually untrusted code within that shared sandbox.

The Python client has no external dependencies. It is automatically installed in
OpenSandbox, Daytona and Cloud Run sandboxes. It is available to commands started
by this agent's `execute` tool, not to independently started sessions or notebooks.

### Limits and recovery

The initial implementation serializes sandbox MCP calls per agent. Defaults are
200 calls per agent per run, 1 MB of arguments, 16 MB of serialized result, and a
15-minute maximum wait per approval or OAuth request. Operators can configure
`SANDBOX_MCP_MAX_CALLS`, `SANDBOX_MCP_MAX_REQUEST_BYTES`,
`SANDBOX_MCP_MAX_RESULT_BYTES` and `SANDBOX_MCP_OPERATION_SECONDS`. The SDK's
`timeout` defaults to 840 seconds; set an appropriate `execute` timeout too. The
run's overall wall-clock limit still applies.

Stopping the run, losing the sandbox, or exceeding those timeouts can interrupt
code. Python execution state is not restored across runs. Network failures and
uncertain write outcomes are **never automatically retried**; inspect the remote
state before repeating a write. Retrying the same bridge operation ID cannot
execute it twice within an active session, even after its result metadata expires.
Supply `operation_id=<UUID>` to `call` or `call_to_file` to reuse a known operation.
Exceptions expose `.operation_id` and include it in their message, including when
the POST response was lost. Keep this ID to recover an uncertain write within the
same active run. Reusing it with different tool arguments is rejected. The client
retries transient failures of the idempotent result GET within the call deadline;
it never automatically retries the POST.
